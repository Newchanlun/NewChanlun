## 一、范围与现状

本 ADR 只裁验收证据、报告结构和关票簿记，不交付运行证据，不提前关闭 #1279、TB-11（#1369）或任何实施票。

ADR 0063 的迁移协议合入不等于 #1368 与 #1402 的非空迁移、回退与恢复已经验收。ADR 0058 的 AT-14 仓内报告路径继续有效。新整图输入包、整图报告与独立总验报告按现行仓外交付 manifest（`.sandcastle/CODEX-CHILD.md:54, :58-63`）管理，不将某台机器的绝对路径写成永久报告身份。

本 ADR 不签署真实资金、账户或场所激活、量档容量、成本与风险阈值、闸门后参数值及凭据权限；这些事项仍适用 ADR 0036:29-33 与 ADR 0041:46 的授权硬门。

## 二、AT-18 逐项证据与整图覆盖义务

每项 Destination 记录固定包含：Destination 编号与完整义务，实施票、范围与精确 commit，覆盖最终产品差异的非作者独评及所审 commit，实际 `origin/main` SHA 与适用 CI run，按 `evidence_class`（仅限 `simulation`、`experiment`、`production` 三值，拒收 `dry-run`）分列的实体报告引用，下游票状态与剩余义务，以及 `"PASS"` 或 `"FAIL"` 结论。

受测场所、隔离、带仓迁移、闸门后参数与 SPEC 全量覆盖核验须同时满足以下五项接口：

1. **证据类严格分列（ADR 0028:48, :70-71；ADR 0062:104, :258；ADR 0063:78-79, :120；CONTEXT.md:373-375）**。每条验收证据必须标明 `evidence_class`。`P1`（`experiment`，如 `P1-hl-testnet`）证据与 `production`（`P2`）证据在 Destination 记录、TB 汇总与整图报告中分槽记录，不得混记，不得以 `P1` 证据冒充生产有效，也不得将 `P1` 拒发语义外推为 `production` 已裁。已启用证据类槽位统一使用 `ArtifactRef[]` 数组（该槽位在当前记录无条目时填 `[]`）；未启用部署槽位（如本图 #1561 下尚未启用的 `production`）统一填 `null`，不得填 `[]`，并保留「生产首次新发送前」具名门。
2. **Destination ⑤ 权限证据三层与能力 hash（ADR 0062:51-79, :258-259）**。Destination ⑤（「目标部署的隔离和权限证据」及 paper 与 live 共核关系）按受测 `evidence_class` 分列核验三层权限证据：（a）授权声明，即场所 profile 记录中由用户签署的 `credential_scope.class` 与 `authorization` 行；（b）场所权限事实，即 #1770 能力记录 `session_permission` 来源栏登记的场所文档 URL、取回日期与 `sha256`；（c）运行时核验，即 X 库启动记录中发送门第 4 至 7 步核验结果与观测记录。三层分开记录，缺任一层或以一层替代另一层均不得记权限证据成立，Destination ⑤ 必须判 `"FAIL"`；已启用场所槽位缺某层证据或缺能力记录时，按第五节 `PermissionSlot` 规则把该层字段或 `capability_hash` 填 `null` 记录缺失，不把整个槽位填 `null`。整体验收的能力 hash 固定取 `(capability_record_version, capability_record_sha256, venue_profile_sha256)` 三元组，同版本异内容或顶层与 Destination ⑤ 分槽值不一致即判冲突失败。
3. **带仓迁移与回退四项不变量（ADR 0063:120, :123）**。涉及旧入口终态、发送隔离与带仓迁移的核验（Destination ②、③、⑤ 及 #1368、#1402）必须基于非空持仓、未结单、费用尾、中断恢复与回退的实际运行证据，逐项确认不丢权利、不复制资金、不双写、不补发四项同时成立，并按 `experiment` 与 `production` 分槽写入顶层 `migration_invariants`；空仓样例或仅合入协议文书不计通过。
4. **闸门后参数触达与启用三记录核验（ADR 0036:25-33, :42）**。TB-11 整图对账与关图按已启用 `experiment`、`production` 部署槽位分槽核验闸门后参数协议，每个槽位恰好处于 `PostGateSlot.status` 四种状态之一：（1）`TRIGGERED_AND_ENABLED`，该 profile 下已启用阶段能力（`growth_enabled=true`）或声明闸门后参数生效时只能取此状态，必须同时出示同一 `profile_id` 与 `evidence_class` 下持久互引的触达事件（`GateReachedEvent`）、参数版本与首次启用三条记录，且严格满足 `触达.known_at < 版本.authorized_at < 首次启用.known_at`（`TestOnly` 或历史双跑的 `SimulatedGateReached` 不计激活，`experiment` 版本不得自动迁入 `production`）；（2）`TRIGGERED_VERSION_AUTHORIZED`，即已发生 `GateReachedEvent` 且参数版本已授权落盘，但首次启用尚未记录（ADR 0036:28, :33），必须出示触达事件与参数版本两条记录，满足 `触达.known_at < 版本.authorized_at`，并核实 `growth_enabled=false`；（3）`TRIGGERED_AWAITING_POLICY`，即已发生 `GateReachedEvent` 但尚未签署参数版本，必须核实输出保持 `AwaitingPolicy{post_gate_params}` 且 `growth_enabled=false`；（4）`NOT_TRIGGERED`，即该受测运行未触发 `growth_eligible=true`，必须出示未触达与未启用证据。状态（2）至（4）均不按已激活处理，必须在 `bounded_domain_statement` 如实记账，并在 `unexecuted[]` 以 `required=false` 列入该槽位的 `ADR_0036_POST_GATE_EXPERIMENT` 或 `ADR_0036_POST_GATE_PRODUCTION` 条目（常量见第五节 `unexecuted[]`）。本条是 ADR 0036:33「TB-11 关图须出示三条记录」的适用范围读法：对 `growth_enabled=true` 或声明闸门后参数生效的每个槽位，三条记录是必出项；对闸门未触达或阶段能力尚未启用的槽位，关图义务由未启用证据（`non_activation_evidence`）与上述 `required=false` 条目销项。
5. **97 故事、345 family 条目与 496 细项逐项对账（`.chanlun/review-results/issue1340-publication-20260909/view/inputs/TB07-11-EXECUTION-SLICES.md:278, :290`；`.chanlun/review-results/issue1339-r2-spec-20260909/view/spec/IMPLEMENTATION-CROSSWALK.md:5, :115`）**。#1391 必须对照 `IMPLEMENTATION-CROSSWALK.json` 逐条核完 97 个故事、345 个 family 条目与 496 个细项验收输入，写入顶层 `spec_coverage` 供 #1403 逐条复核。crosswalk 条目带 `exclusion_boundary=true` 的 family 条目（所绑定 crosswalk 上是 `OE41` 与 `OE45`）只核排除与防混用边界，其余 family 条目全部是必需条目。`OE42` 是必需条目，#1391 须核实覆盖输入为它登记的 `OUT_OF_SCOPE_PRESERVE` 处分得到遵守（规则见第五节 `SpecCoverageLedger`）。不得仅凭测试计数、子票关闭率或 `N=2` 样例代替逐子义务核验。

组件证据、协议裁定、局部成功、正确拒绝、空域、仅 schema 或未执行测试均不得代替必需成功路径。缺证、跨证据类冒充或射程不符即不得判 `"PASS"`。

## 三、TB-01..11 关票门

关票通用门（`.sandcastle/docs/graph-engineering.md:237-241`）要求票面验收全部满足，全部必需子片交付，非作者评审覆盖最终产品差异，产品进入 `origin/main`，适用必需检查通过，实体报告可读并绑定版本，在制品已有合法处置。失败、未构造、未执行、权限阻塞及跨 TB 未闭合的联合义务必须保留为未完成，不得记为已处置失败。

为消除整图报告生成、#1391 交付关票与 TB-11（#1369）关票门之间的先后循环（`.sandcastle/CODEX-CHILD.md:54`；`.sandcastle/docs/graph-engineering.md:237, :240`），并拦截未经 #1403 独立总验的自报通过（`.sandcastle/CODEX-CHILD.md:74`），`tb_summaries[]` 与 TB-11 关票按三阶段无环推进：

- **`TB-01..TB-10` 独立关票门**。`tb_summaries[]` 中 `TB-01..TB-10` 每项固定核验 TB 编号与票号、全部内部实施子片、按 `evidence_class` 分列的完整外部行为实际运行证据（其中 TB-08、TB-09、TB-10 的 `experiment` 与 `production` 严格分槽，TB-10 并须在自身非空迁移证据上满足 ADR 0063:120 四项不变量）、最终非作者独评、实际 `origin/main` SHA、适用 CI run、各自已落地的实体报告（`entity_reports` 非空，`input_bundle` 固定为 `null`）、剩余义务与票状态。全部满足且票已合法关闭记 `gate_satisfied=true`；任一未满足记 `gate_satisfied=false` 并使整图判 `"FAIL"`。
- **`tb_summaries[TB-11]` 前置实施门（#1391 生成报告时）**。`tb_summaries[TB-11]` 记 `gate_satisfied=true` 要求 TB-11 自身两张实施子片（#1391 逐项对账与报告生成器、#1403 独立总验器）的实现代码均已进入被审 `origin/main`（`tb_summaries[TB-11].main_sha` 与两项 `slices[].main_sha` 均非 `null` 且为顶层 `head` 在 `origin/main` 上的祖先提交）、适用必需 CI run 结论全部为 `"SUCCESS"`、两子片最终代码差异均获非作者独评 `"PASS"`，并在专用字段 `input_bundle` 中绑定供 #1391 与 #1403 共同消费的 `at18-input-bundle/1` 清单 `ArtifactRef`（非 `null`）。整图业务运行证据归各 Destination、`TB-01..TB-10`、`spec_coverage`、`migration_invariants` 与 `post_gate_records` 承载，故 `tb_summaries[TB-11]` 的 `evidence_by_class` 在已启用证据类槽位固定填 `[]`、在未启用 `production` 槽位固定填 `null`，`entity_reports` 固定填 `[]`，不写入本次 `at18-report/1` 自身路径、`sha256` 或 `content_hash`。正式整图报告由 #1391 在 `OPEN` 状态生成（顶层 `ticket` 固定填 `1391`），报告生成时不要求 #1391、#1403 或 #1369 预先关闭（此时 `tb_summaries[TB-11].ticket_state` 及 #1391、#1403 的 `slices[].state` 均如实记 `"OPEN"`，代码与 `input_bundle` 前置齐备即记 `gate_satisfied=true`）；任一子片代码未进入 `origin/main`、CI 未绿、独评未过或输入包缺失、不可读时必须记 `gate_satisfied=false`，输入包缺失或不可读时 `input_bundle` 填 `null`，并为每项未满足的前置写入一项 `FailedCheck`。
- **`#1391` 封包关票、`#1403` 独立总验关票与整图关票序**。#1391 在 `origin/main` 确切 `head` 上产出 `at18-input-bundle/1` 与 `at18-report/1` 后，经 #1391 仓外 delivery manifest（同批登记两份仓外产物）预检通过（退出码 `0`）且获非作者最终独评 `PASS`，先行关闭 #1391。随后 #1403 在独立总验会话中对同一 `origin/main` `head`、#1391 的 delivery manifest、`at18-input-bundle.json` 及 `at18-report.json` 实际运行复核，产出仓外 `at18-verification/1`（顶层 `ticket` 固定填 `1403`，单向绑定 #1391 manifest、`at18-report.json` 与 `at18-input-bundle.json`），经 #1403 仓外 delivery manifest 预检通过且获非作者最终独评 `PASS` 后关闭 #1403。仅当 #1391 与 #1403 依次合法关闭且结论均为 `"PASS"` 后，方可关闭 #1369、SPEC #1340 与 #1323。

## 五、`at18-input-bundle/1`、`at18-report/1` 与 `at18-verification/1`

整图对账与独立总验采用三份具名版本化仓外记录：输入运行包清单 `at18-input-bundle/1`（`at18-input-bundle.json`）、整图验收报告 `at18-report/1`（`at18-report.json` 及从同一份 JSON 确定性渲染的 `summary.md`，人读摘要不作独立判定）和独立总验回执 `at18-verification/1`（`at18-verification.json`）。三份产物均置于仓外持久证据目录，按 `.sandcastle/CODEX-CHILD.md:56-63` 与 `.sandcastle/delivery-bundle.ts:10-17, :27-38` 由所属票的仓外 delivery manifest 以 `storage: "external"` 绑定 `ticket`、`base`、`head`、路径及文件字节 `sha256`；移动或归档后更新 manifest 并重验。

规范化、`content_hash`、提交祖先与封闭类型规则（对齐 ADR 0025:30 与 ADR 0058:193, :208）：

- **`content_hash` 无自指计算口径**。对 `at18-input-bundle/1`、`at18-report/1` 或 `at18-verification/1` 移除各自顶层 `content_hash` 键后，将其余完整 JSON 对象按 RFC 8785（JCS）规范化为 UTF-8 字节串，求 64 位小写十六进制 `sha256` 写入顶层 `content_hash`。`content_hash` 绑定结构化语义内容，仓外 delivery manifest 的 `sha256` 绑定落盘文件完整字节，两者均不产生自指循环。
- **封闭字段集合与升版边界**。三份 schema 的顶层和全部嵌套对象均为封闭字段集合，禁止未声明额外键；总验器（#1403）遇到缺失必填键、类型不符、枚举越界、固定长度数组长度不符、`content_hash` 不匹配或未声明额外键即拒收判 `"FAIL"`，并按下条输出回执。新增、删除、重命名字段或改变字段语义均须升版为 `/2`。
- **形状规则与判定规则分层**。本 ADR 的约束分两层。形状规则只有以下几类：三份 schema 顶层与全部嵌套对象的封闭键集；各字段的声明类型（含 `Sha256Hex`、`GitCommitSha`、`UtcTimestamp` 的格式、正整数，以及 `ArtifactRef` 按 `storage` 区分的 `commit`、`ticket`、`base`、`head` 取值组合）；枚举取值；`schema_version` 常量；文档自身 `content_hash` 按上条口径与其内容相符；`destinations[]` 6 项、`tb_summaries[]` 11 项、`legacy_dispositions[]` 7 项的固定长度与顺序；写入方自己决定的常量与槽位编码（如 `TB-01..TB-10` 的 `input_bundle` 固定填 `null`、未启用槽位填 `null`）。只有违反形状规则的文档形状不合法，由 #1403 拒收。其余约束都是判定规则，包括字段非 `null`、数组非空、跨字段或跨文档相等、哈希或摘要相符、文件可读、命中 manifest、祖先关系、时序、与 crosswalk 逐条对应的项数，以及状态与证据的搭配。判定规则不满足时照常写出记录：字段记实际观测值，证据缺失或不可读处按字段类型填 `null` 或 `[]`，在 `failed_checks[]` 写入一项 `FailedCheck`，所在记录的结论取失败值（报告 `overall_result="FAIL"`、回执 `verdict="FAIL"`、TB 汇总 `gate_satisfied=false`、覆盖条目 `status="FAIL"`）。本 ADR 写作「PASS 要求」的条件，以及落在判定规则上的「必须」「须」「非 `null`」「非空」「等于」「一致」「恰好」，都只约束取通过值的记录，不约束失败记录的形状。每份文档的身份字段（`schema_version`、`content_hash`、`ticket`、`base`、`head` 与 `generated_at` 或 `verified_at`）只取自该文档自身及登记它的本票仓外 delivery manifest，始终非 `null`，取不到时不写出该文档（见下条「引导前提与无文档结果」）；它与其他文档的任何关系（`head` 相等、哈希相符、命中 manifest）都是判定规则。输入包不承载结论，必需输入缺失时不生成输入包，由报告的 `tb_summaries[TB-11].input_bundle` 与回执的 `input_bundle_ref` 填 `null` 记录缺失。#1403 引导成功后，遇到受验对象缺失、不可读或形状不合法时，仍输出形状合法的 `at18-verification/1`：身份字段取自 #1403 自身 manifest；#1391 的 delivery manifest 可读且通过 `deliveryManifestSchema` 校验时，`report_manifest` 填指向它的 `ManifestRef`，否则填 `null`；`report_ref` 与 `input_bundle_ref` 照录该 manifest 中形状合法的对应登记，无此登记时填 `null`；`report_content_hash` 按下文「派生值」规则取重算值或 `null`；每个缺失、不可读或形状不合法的受验对象各写一项 `FailedCheck`（`scope` 写明受验对象与字段路径），并判 `verdict="FAIL"`。
- **引导前提与无文档结果**。上条「照常写出记录」以写入方能写出形状合法的文档为前提；本条定义该前提不成立时的唯一结果。#1391 写出 `at18-input-bundle/1` 与 `at18-report/1`、#1403 写出 `at18-verification/1` 之前先完成引导，依次为：（1）读取本票仓外 delivery manifest（此时可尚未登记本次产物），它须可读且通过 `deliveryManifestSchema` 校验，并通过本步下列已登记实体校验，文档的 `ticket`、`base`、`head` 只取自它，不取自受验对象、调用参数、环境变量或当前 Git 状态（`HEAD`、分支、`origin/main`）；（2）写 `at18-report/1` 时，`destinations[]`、`tb_summaries[]`、`legacy_dispositions[]` 各固定项中类型不含 `null` 的非结论字段（`id`、`obligation`、`tb_id`、`ticket`、`ticket_state`、`disposition`）均取得实际值，取不到时不以猜测值代填；（3）待写内容能按本节 `content_hash` 口径规范化，写入方照录的字符串含孤立代理码点等不能规范化的内容时不原样写入，改在 `FailedCheck.detail` 中描述，如此处理后仍不能规范化才算本步失败；（4）先写临时文件，再改名到输出路径。任一步失败时，该工具不写出该类型文档，输出路径上不出现该文档；它沿用 `.sandcastle/delivery-bundle.ts:116-132` 预检失败载体，在标准输出写出 `status: "BLOCKED"` 与 `diagnostics[]`（元素为同文件的 `DeliveryDiagnostic`，`code` 按上述四步依次取 `MANIFEST_UNREADABLE`、`INVALID_MANIFEST` 或本步的实体预检诊断，其余依次为 `FIXED_ITEM_UNAVAILABLE`、`CONTENT_NOT_CANONICAL`、`OUTPUT_WRITE_FAILED`），并以退出码 `1` 结束（与 `.sandcastle/delivery-bundle.mts:13` 对 `BLOCKED` 的退出码相同）。第（1）步失败时 #1391 两份文档都不写出。消费方以输出路径上有无该文档判断，不从退出码推断；`BLOCKED` 载体不是文档，不得登记进 delivery manifest，也不能代替输入包、报告或回执。各消费方对缺失文档的处理如下：没有输入包时，报告的 `tb_summaries[TB-11].input_bundle` 与回执的 `input_bundle_ref` 填 `null` 并判失败；没有报告时，#1403 按受验对象缺失输出 `verdict="FAIL"` 的回执；没有回执时不存在 `verdict="PASS"` 的 `at18-verification/1`，本节末段关票门不成立。引导成功后，才适用「受验对象缺失、不可读或形状不合法时仍输出 12 键 `verdict="FAIL"` 回执」。
  - 引导第（1）步校验本票 manifest 中**已登记**的实体。逐项检查 `reports[]` 以及 `reviews[].report`、`checks[].evidence`、`scan.evidence`、`scan.disclosure.triage` 的已有引用。按 `.sandcastle/CODEX-CHILD.md:54-63` 和 `.sandcastle/delivery-bundle.ts:189-241` 核完整声明、存储、路径、普通文件、可读性和版本绑定。仓内实体从自身 manifest 的 `head` 读 Git blob，不用当前工作树替代；仓外实体按 `externalReportsRoot` 和本票 `ticket/base/head` 读取。两者均重算完整文件字节的 SHA-256，与登记值精确比较。本步实体诊断限于 `DUPLICATE_ENTRY`（`reports[]` 路径重复）、`UNDECLARED_REPORT`（已有实体引用未在 `reports[]` 登记）、`REPORT_DECLARATION_MISMATCH`、`REPORT_VERSION_MISMATCH`、`INVALID_REPORT_PATH`、`REPORT_NOT_REGULAR_FILE`、`REPORT_MISSING`、`REPORT_NOT_IN_HEAD`、`REPORT_HASH_MISMATCH`（实际摘要不符）。任一失败走第（1）步的 `BLOCKED`，退出码 `1`。在任何临时或正式产物写入前返回，不创建、改名或覆盖文件；#1391 的输入包、报告及 `summary.md` 均不写，#1403 的回执也不写。
  - 未登记本次待生成产物的清单仍可引导。不在引导阶段执行 `requiredReports` 或空 `reports[]` 的完整性检查（`MISSING_REPORT_DECLARATION`、`REPORT_DECLARATION_REQUIRED`）；封包关票仍按第三节运行完整预检。上游或受验清单的实体摘要不符不是自身清单引导失败，按本节判定规则使报告或回执为 `"FAIL"`。
- **派生值**。由另一份产物计算得出的字段，只在计算链每一步都对该产物现有字节成功、且未作任何修复时取计算值；任一步失败时取该字段的缺失值，写一项 `FailedCheck`（`check_id` 为失败步骤 `FILE_READ`、`JSON_PARSE`、`JCS_CANONICALIZE` 或 `SCHEMA`，`detail` 写失败结果），所在记录取失败值。四步依次为：读取文件（`storage="in_repo"` 时读取 `commit` 上的 Git blob）；严格解析为 JSON 对象（RFC 8259 语法、合法 UTF-8、无重复键、顶层为对象，不以后出现的重复键覆盖前者）；按 RFC 8785 规范化（`1e400` 等非有限数值与 `"\ud800"` 等孤立代理码点在此步失败，不得用 `JSON.stringify` 把非有限数值写成 `null` 或保留坏码点冒充成功）；按所属 schema 校验。各派生字段只走自己需要的步骤：文件字节摘要（`ArtifactRef.sha256`、`ManifestRef.manifest_sha256`、`VenuePermissionFact.sha256`、`CapabilityTuple` 的两个 `sha256`、`SpecCoverageLedger.crosswalk_sha256`，以及 `tb_summaries[TB-11].input_bundle` 的摘要）只需读取；`report_content_hash` 需读取、解析与规范化，不经 schema，故 schema 不合法但能规范化的报告保留重算值；`report_manifest`、照录自它的 `report_ref` 与 `input_bundle_ref`，以及 `external_manifests[]` 各项需全部四步（schema 为 `deliveryManifestSchema`）；`spec_coverage` 的 `stories`、`families`、`details`（含项数、顺序与 `entry_mode`）、`CapabilityTuple.capability_record_version`、`VenuePermissionFact` 的 `source_url` 与 `retrieved_at`、`PostGateSlot` 的三个时间戳需读取、解析与所用字段的校验。缺失值按声明类型取：可空字段填 `null`，数组填 `[]`；`ArtifactRef`、`ManifestRef`、`CapabilityTuple` 或 `VenuePermissionFact` 的任一字段算不出时整条不写，所在可空字段填 `null`，所在数组不列该项；可变长数组的元素有类型不含 `null` 的字段取不到时，不列该元素（如缺 `artifact` 的 `ReviewRef`）。`at18-input-bundle/1` 的 `spec_ref`、`crosswalk_ref`、`coverage_input_ref` 不可为 `null`，任一算不出时按「形状规则与判定规则分层」不生成输入包；这是判定失败，不是引导失败，不出 `BLOCKED`。文档自身的 `content_hash` 不是派生值，由「引导前提与无文档结果」第（3）步约束。
- **`origin/main` 祖先提交一致性**。正式通过报告顶层 `head` 必须等于对账时的实际 `origin/main` SHA；报告内全部 `destinations[].main_sha`、`destinations[].commits[]`、`tb_summaries[].main_sha`（非 `null` 时）、`tb_summaries[].slices[].main_sha`（非 `null` 时）与 `ArtifactRef.commit`（`storage="in_repo"` 时）均必须为顶层 `head` 在 `origin/main` 上的可达祖先提交（`git merge-base --is-ancestor` 为真），否则判 `"FAIL"`。`ArtifactRef.head`（`storage="external"` 时）取自上游仓外 delivery manifest 的 `head`（是否命中该 manifest 按 `ArtifactRef` 规则核验），预检要求该 `head` 等于交付工作区的 `HEAD`（`.sandcastle/delivery-bundle.ts:147`），即合入前的交付分支头；交付可由 squash 或 merge commit 合入（`.sandcastle/docs/graph-engineering.md:238`、`.sandcastle/deepagents-pilot/pilot1742/review_sweep.py:276-279`）；squash 后分支头可以不是 `origin/main` 的祖先。`ArtifactRef.head` 因此必须满足以下两项之一，否则判 `"FAIL"`：（a）它是顶层 `head` 的可达祖先提交；（b）GitHub 记录存在已合入 `main` 的 PR（`merged=true` 且 `base.ref="main"`），其 `head.sha` 等于 `ArtifactRef.head`，且其 `merge_commit_sha` 是顶层 `head` 的可达祖先提交。该 PR 归属 `ArtifactRef.ticket` 的依据是对应 `ManifestRef` 已把同一 `ticket` 与 `head` 绑定，不从 PR 标题或正文推断；PR 按 `head.sha` 查得，报告不记录 PR 编号。（b）项只证明该 `head` 已合入 `main`，不证明 GitHub 把该 PR 记在 `ArtifactRef.ticket` 名下；票归属只取 `ManifestRef` 的绑定声明，由该票自身按第三节关票通用门完成的交付验收认可，#1391 与 #1403 均不得把（b）项成立当作票归属已核实。#1403 独立复核本规则，（b）项须自行向 GitHub 查询，不采信报告结论。

### 子义务覆盖门

#1391 与 #1403 独立从同一输入包重建期望键，不从观察、证据原件或覆盖声明反推分母。先按下表取每个 `(kind, id, slice_id, obligation)`。数组下标从 0 起；`obligation={path,sha256,pointer}` 的路径和文件摘要取表中的输入包引用，`pointer` 按 RFC 6901。定位不存在、ID 不等、条目或切片重复即失败。规范节点及其既有适用约束全部生效，指向同一 ID 的另一份规范、子节点或祖先节点不匹配。

| `kind` | `id` | `obligation` 的规范节点 | `slice_id` |
|---|---|---|---|
| `story` | crosswalk `rows[i].story_id` | `crosswalk_ref` 的 `/rows/i` | `rows[i].success_closure_slice_ids` 各值 |
| `family` | crosswalk `family_entry_links[i].id` | `coverage_input_ref`，指针取该行 `source_json_pointer`，所指 `id` 必须相同 | 该行 `success_closure_slice_ids` 各值 |
| `detail` | crosswalk `detailed_acceptance_links[i].id` | `coverage_input_ref`，指针取该行 `source_json_pointer`，所指 `id` 必须相同 | 该行 `success_closure_slice_ids` 各值 |
| `destination` | crosswalk `destination_success_obligations[i].destination_id` | `crosswalk_ref` 的 `/destination_success_obligations/i`；还须核同 ID 在 `coverage_input_ref.destinations[]` 的完整义务、链接各条目与第二节专用门 | 固定 `null`：Destination 本身是汇总，不发明关闭切片 |

`slice_id="TB-11"` 的键按既有 `SpecCoverageLedger` 只用 TB-11 前置门与共同输入包核验，不需要下述映射，也不使同一条目的其他切片免证。其余每个四元组从 `at18-coverage-domains/1` 的同键行展开为一个或多个完整期望键 `(kind,id,slice_id,obligation,evidence_class,profile_id)`，具体规则如下：

1. **先冻结受测域**。补件票先交付 `.chanlun/at18/coverage-domains.json`，由非作者按绑定规范、已批准的切片义务、部署和 profile 合同逐行核足应核域及来源票，再合入 main。文件以输入包 `head` 上该固定 Git blob 为准，不接受参数指定替代文件。两端按补件票交付回执核该 blob 所属已合主线的 scope PR、独审 run 和该文件摘要。顶层固定 `{schema_version: "at18-coverage-domains/1", owner_ticket, rows}`，每行为 `{kind,id,slice_id,obligation,domains}`，每个域为 `{evidence_class,profile_id,required_result,deferred_gate,scope_refs,source_tickets}`。每个非 TB-11 四元组恰有一行，`domains` 非空且类与 profile 的组合不重复；不得多填、漏填或合并四元组。`scope_refs` 非空，元素为带稳定定位的 `{artifact,locator}`，指向批准的切片/部署/profile 依据；`source_tickets` 是该域可提供证明的原交付正整数票号集合，不含补件票。
2. **域记录不决定放行**。`evidence_class` 只能取第二节三值；`profile_id` 取相应具名版本的 profile ID，只有所指规范不要求 profile 时才为 `null`，并由审查逐行核定。同一义务确需多个域时列全，不能按已有结果选择域；仅因已有原件为 `simulation` 不能把 `experiment` 改为 `simulation`。启用及受测证据依第二节。预期结论 `required_result` 只能取 `VERIFIED|PRESERVED_BOUNDARY|BOUNDED_DEFERRED`；边界与延期只能在本 ADR 已准的条目和域使用。延期额外要求 `deferred_gate` 精确匹配一个已准具名门、对应的 `required=false` 未执行项和该门的实际状态，其他结论该字段为 `null`。未启用生产槽不新增生产的运行要求。静态证明和处分可证明相应判据，不冒充运行。域文件的非作者评审须明确绑定完整文件字节、来源版本、分母和域；修改范围或绑定规范文件摘要变化时，补件票的后继交付先重核受影响域，再重签映射。旧摘要下的声明不得迁用；其他不变的真实原件可继续引用。变更不得为消除缺证而缩分母。
3. **补件票承担映射**。第六节指定的补件票在仓外封包一个 `at18-evidence-scope/1`（`at18-evidence-scope.json`），顶层固定 `{schema_version: "at18-evidence-scope/1",domains_sha256,claims}`。`domains_sha256` 绑定第 1 项固定 Git blob。`claims` 每项固定 `{kind,id,slice_id,obligation,evidence_class,profile_id,result,deferred_gate,records}`。禁止期望集外的键，同键只能有一项；`result` 取期望结论之一或 `EXCLUDED`，后者永不计作支持；其他结论的 `records` 必须非空。每条记录固定 `{source_ticket,main_sha,tested_head,run_id,artifact,locator}`。`locator` 与 `scope_refs` 共用二选一的形状：`{json_pointer}` 指可解析的严格 JSON，或 `{first_line,last_line}` 指合法 UTF-8 原件上从 1 起、两端含的 LF 行区间；不得指回映射、独审收据或 AT-18 本次输出。运行记录的 `run_id` 取已交付会话身份；历史原件未内嵌 ID 时，取已验回执中唯一运行锚点的 `sha256`、定位和受测提交组成的身份，由独审核定。同次运行在各声明使用同一身份，非运行事实填 `null`。
4. **独审逐键出收据，机器核绑定**。补件作者不得替代来源方写运行结果。异于补件作者且与 #1391、#1403 运行方分离的非作者复核者，读取每个期望键的完整规范、实际原件节点及受测上下文，逐项核对授权域、范围、判据与反证。#1391 与 #1403 不从自然语言猜 PASS，只接受补件票已验收清单在 `reviews[].report` 登记的该人原件 `at18-evidence-review/1`（`at18-evidence-review.json`）。顶层固定 `{schema_version: "at18-evidence-review/1",ticket,reviewer,review_run_id,reviewed_head,domains_sha256,scope_sha256,claims}`；`claims` 为与映射数组同序的 `{index,verdict}`，从 0 起且每个下标恰一次，`verdict` 为 `PASS|BLOCK`。复核者仅在对应记录覆盖该键全部判据、没有反证时记 PASS；001 原件不能为 002 签 PASS。收据同时绑定两份完整字节摘要及该票精确交付 head。机器逐键核期望键、结论和延期门等值，并用已验收交付回执核收据的审查身份、独立审查 run、head、摘要和下标。本票清单之外的副本、别次独审、重用旧摘要或未带该收据的映射均不计。收据中的 PASS 不能覆盖原件可机读的冲突：原件自带的 ID、类、profile、run 身份或结果与声明冲突时立即拒收；不允许在同一运行选取有利的冲突记录。
5. **源和引用不能互换**。映射与收据的外部 `ArtifactRef.ticket` 与 `owner_ticket` 均取补件票号，由该票冻结交付 manifest 绑定。机器从 #1391 原生 `blocked_by` 回查该票，并核第六节的父票、票题以及该票已验收交付的精确版本及唯一登记的映射、收据；多份可匹配而回执不能区分时拒收。记录的 `source_ticket` 必在该域的 `source_tickets` 内；按第三节及来源票的 resolution 核其实际 `main_sha`、已验收原件登记。仓外原件的票号须等于 `source_ticket`，仓内原件须在该来源票回执精确指认的 Git blob 上。按本节 `ArtifactRef` 规则查完整字节，适用时再查原件自身 schema 和摘要；实际运行的 `tested_head` 对应 `main_sha` 的产品树须相等或只差下文定义的纯报告尾部。文件和定位可跨键复用，收据不能跨键借用。覆盖声明缺失、键不匹配、明确排除、原件不支持或未获逐键 PASS 时记 `COVERAGE_SCOPE`，在 `scope` 写条目、切片与域，在 `detail` 写规范定位及原因；所在条目和整图失败。

上述三种补件记录都是上游证据，不新增三份 AT-18 产物的键。#1391 在原有 `evidence_refs` 或 Destination 的 `evidence_by_class` 登记支持条目的映射引用（仅填合法已启用槽）。#1403 从报告、输入包 `head`、映射、独审收据与实际原件重算，不消费 #1391 私有观察。输入包 `external_manifests[]` 登记补件票的清单以及域依据、映射的全部上游仓外清单。域文件或正本绑定缺失属于覆盖判定失败，记 `COVERAGE_SCOPE`，不当作本票清单引导失败。专用 TB、权限、迁移等槽仍按各自已有规则核真实原件，不以此映射替代。覆盖取证规则在首份正式 /1 报告前生效；不改变三份 /1 schema、槽位含义或既有 AT-14 原件及路径。

### 适用 CI 与最终独评的落地绑定

沿用 [交付与关票](../../.sandcastle/docs/graph-engineering.md#交付与关票) 与 [一次收齐交付材料](../../.sandcastle/CODEX-CHILD.md#一次收齐交付材料)。以每个实施票或必需子片已核交付的实际落地提交 `M` 为对象。汇总不能拿其他子片的绿灯补齐本片。沿被审 `head` 的第一父链核 `M`，不把合入的候选父提交当主线。交付方提供 manifest、确切落地记录和 CI/评审原件。#1391 从 GitHub 和 Git 对象重算，#1403 独立取得同一类原件重算。

**最终独评**。读取已验收的非作者原件，核审查身份、所审 `E` 和 PASS，并验证最终交付差异已完整受审。对每个 `M` 固定以 `M^1→M` 为实际落地差异，多提交交付逐落地点核验。对所有差异按 `path,before_blob,before_mode,after_blob,after_mode` 排序比较，增删的空侧记不存在，改名算删加。非产品项必须同时满足 `.sandcastle/delivery-bundle.ts:248-253` 的分类和非作者原件用同路径、同前后字节及 mode 明确核定的纯文档、报告或机械收据；凡作运行、构建、测试、CI 输入或权限/类型变化的都不剔除。未知按产品处理。

- `E=M` 时，以原件验证实际落地的最终差异；`E` 是主线第一父链上的报告尾部前后提交时，比较 `E` 与 `M` 两棵树，且第一父链两端间每步只可有上述非产品变更。独评仍须覆盖原产品差异。
- `E` 属于 PR 候选时，读取 GitHub 本仓已合入 `main` 的 `head.sha=H` 与 `merge_commit_sha=M`。核对应已验收来源票。按实际合入时已生效的正式门核精确 `H`；现行要求 `deepagents/review`、`ci-ok`、适用必需检查和 strict。若 `E≠H`，仅接受 `git merge-base --is-ancestor E H` 且 `E..H` 内所有提交对其每个父的差异均只是上述非产品尾部；仍核 `E` 原件覆盖最终差异。
  - **squash**：`M` 只有一个父 `P`，且 `P` 是 `H` 可达祖先；比较 Git 实得 `P→H` 与 `P→M` 的完整产品差异。
  - **merge commit**：`M` 恰有两父，第一父为实际旧主线 `P1`，第二父须为 `H`。`tree(M)=tree(H)` 时产品等价，仍核独评实际范围覆盖 `P1→M`。树不同时，取唯一 `B=git merge-base --all P1 H`，比较 `B→H` 与 `P1→M` 的完整产品差异。合并时新增或改变产品路径、前后内容或 mode 任一不同须在 `M` 补审。实际对象不可读、候选不对应或有多个 merge-base 时，不证明等价。

独评不覆盖最终差异或关联不可核实，记 `REVIEW_FINAL_PRODUCT`；不把仓外引用的合入关系当独评。不把扫描旧运行改写成在新 SHA 上执行。

**主线 CI**。取得本仓确切 `M` 的 main push 运行；按该版工作流和当时适用必需检查核对。现行必需主线结果是 `ci.yml` 的 `ci-ok` 与 `devskim.yml` 的 `DevSkim` 成功，`deepagents/review` 核 PR head，不当作 main 作业。应执行作业为 `M` 版 `ci-ok.needs` 所要求的作业及其矩阵项；只以 GitHub 的 workflow 路径、事件、仓库、run ID、实际 head 与 jobs 逐项核实，不能凭 run 总结果替代。按冻结工作流本来不适用的作业不纳分母；缺少适用门、非成功、未执行或无解释的跳过均记 `CI_FINAL_PRODUCT`。

现行 `ci.yml` 的 Rust push 去重只按该运行版规则复算（#1875、#2027；`.github/workflows/ci.yml:41-46,:76-116,:1459-1530`）：

1. 若依赖集合中的 Rust 作业跳过，先证实 `M` 双父，第二父为经确认的 `H` 且 `tree(M)=tree(H)`；以 `M^1→M` 比较完整路径，改名计旧、新两侧，GitHub compare 文件数须非零且小于 300，Git 实得改动集须与之相符，未改 `rust/Cargo.lock`。按该版 `SKIP_RE` 逐路径判断。全部命中时 Rust 不适用，不虚构任何 Rust run。
2. 有跳过集外的路径时，从该 push 的 `changes` 作业 GitHub 原日志取其采用的 PR run ID（原日志已归档时核验已验收回执保存的同一 GitHub 行及其作业身份），核对应本仓 `ci.yml`、`event=pull_request`、同仓 head、精确 `H`、在被主线 `changes` 选用前已成功。该 run 的 `rust-green <指纹>` 与其 Rust 依赖的各个作业和矩阵项均须为 SUCCESS，不能是同 PR 复用的 skipped。按该版 `.github/scripts/ci-rust-reuse.py` 的 `tree_entries/digest` 和 `SKIP_RE` 对 `M` 复算实际 Rust 输入指纹，须与服务端作业名一致。原运行和 PR 来源运行分别照实进入 `CiRunRef[]`，保留各自实际 SHA、run ID 和结果；不得把 PR run 写成 main run。
3. 任一去重前提不可复核即不计已执行。只缺该次跳过的 Rust 实跑时，可用对确切 `M` 的同仓 `ci.yml workflow_dispatch` 全跑回执逐作业补齐。原 main push 的 `ci-ok`、适用 DevSkim 和其他必需检查仍要有实际成功记录。PR run 不替代 main push；独评的 squash 或 merge 差异等价也不替代 CI 的同树去重。

任一 CI 或最终独评门失败，将诊断写入 `failed_checks[]`，所在 Destination 或 TB 判失败。#1391 与 #1403 均不得从最终状态、同仓祖先关系或上游自报推断已运行。

共用子记录封闭类型定义如下（`Sha256Hex` 为匹配 `^[0-9a-f]{64}$` 的字符串，`GitCommitSha` 为匹配 `^[0-9a-f]{40}$` 的字符串，`UtcTimestamp` 为 RFC 3339 UTC 时间字符串，`EvidenceClass` 为 `"simulation" | "experiment" | "production"`，`CiConclusion` 为 `"SUCCESS" | "FAILURE" | "CANCELLED" | "TIMED_OUT" | "ACTION_REQUIRED" | "NEUTRAL" | "SKIPPED" | "STALE"`）：

- `ManifestRef`（5 键）：`{ticket: integer, base: GitCommitSha, head: GitCommitSha, manifest_path: string, manifest_sha256: Sha256Hex}`。`ticket` 为正整数；`manifest_path` 为 checkout 外、无 `..` 的绝对路径。PASS 要求 `manifest_path` 无符号链接、文件可读且字节摘要等于 `manifest_sha256`，内容通过 `.sandcastle/delivery-bundle.ts` 的 `deliveryManifestSchema` 校验且内部 `ticket`、`base`、`head` 与本引用完全一致；任一不满足时，该 manifest 登记的引用不计为证据，在 `failed_checks[]` 写明并判 `"FAIL"`。
- `ArtifactRef`（8 键）：`{storage: "in_repo" | "external", path: string, sha256: Sha256Hex, commit: GitCommitSha | null, ticket: integer | null, base: GitCommitSha | null, head: GitCommitSha | null, bounded_scope: string}`。`storage="in_repo"` 用于仓内规范文件与 ADR 0058 既有仓内报告，`path` 为不含 `..` 的仓内相对路径，`commit` 必填 `GitCommitSha`，`ticket`、`base`、`head` 固定为 `null`；`storage="external"` 用于仓外持久证据（`.sandcastle/CODEX-CHILD.md:61`；`.sandcastle/delivery-bundle.ts:11-16`），`path` 为仓外持久证据目录下无 `..` 的绝对路径，`commit` 固定为 `null`，`ticket`（正整数）、`base`、`head` 均必填非 `null`。PASS 要求：`storage="in_repo"` 的 `commit` 在 `origin/main` 上且 Git blob 摘要等于 `sha256`；`storage="external"` 的 `path` 无符号链接，并在对应 `ManifestRef`（上游仓外证据对应 `at18-input-bundle.json` 的 `external_manifests[]`，#1391 自身产出的输入包与报告对应 `at18-verification.json` 的 `report_manifest`）中存在完全匹配的 `{storage: "external", path, sha256, ticket, base, head}` 条目，且落盘文件可读、字节摘要等于 `sha256`。任一缺失、不可读、未命中 manifest 或摘要不符时，该引用不计为证据，在 `failed_checks[]` 写明并判 `"FAIL"`，禁止跨存储方式回退。报告中缺失的必需证据按所在字段的规则填 `null` 或 `[]`，不写占位引用；`at18-verification/1` 的受验引用另按其定义处理。
- `EvidenceByClass`（3 键）：`{simulation: ArtifactRef[], experiment: ArtifactRef[], production: ArtifactRef[] | null}`。已启用证据类槽位必填 `ArtifactRef[]`（无条目填 `[]`，不得填 `null`）；未启用部署槽位（#1561 下的 `production`）必填 `null`（不得填 `[]` 或非空数组）；`production` 经独立授权启用后同样必填 `ArtifactRef[]`。
- `CapabilityTuple`（3 键）：`{capability_record_version: string, capability_record_sha256: Sha256Hex, venue_profile_sha256: Sha256Hex}`（ADR 0062:258）。
- `VenuePermissionFact`（3 键）：`{source_url: string, retrieved_at: string, sha256: Sha256Hex}`（ADR 0062:51-79）。
- `PermissionSlot`（4 键）：`{authorization_declaration: ArtifactRef | null, venue_permission_fact: VenuePermissionFact | null, runtime_verification: ArtifactRef | null, capability_hash: CapabilityTuple | null}`。已启用场所槽位的前三个字段依次记第二节第 2 条的（a）授权声明、（b）场所权限事实与（c）运行时核验，`capability_hash` 记能力 hash 三元组。某层证据缺失时该字段填 `null`；能力记录或场所 profile 缺失、三元组任一元素无可读来源时 `capability_hash` 填 `null`；不得以占位引用、不可读引用或他层证据代填。任一字段为 `null` 时 Destination ⑤ 的 `result` 必须为 `"FAIL"`，`failed_checks[]` 须为每个 `null` 字段写入一项（`scope` 写明 Destination ⑤ 与槽位），`overall_result` 随之为 `"FAIL"`。整个槽位填 `null` 只表示该场所槽位未启用。
- `ReviewRef`（4 键）：`{reviewer: string, reviewed_head: GitCommitSha, verdict: "PASS" | "BLOCK", artifact: ArtifactRef}`。
- `CiRunRef`（5 键）：`{workflow: string, run_id: integer, head_sha: GitCommitSha, conclusion: CiConclusion, url: string}`（`run_id` 为正整数）。
- `TicketScopeRef`（2 键）：`{ticket: integer, scope: string}`（`ticket` 为正整数，下同）。
- `SliceStatusRef`（3 键）：`{ticket: integer, state: "OPEN" | "CLOSED", main_sha: GitCommitSha | null}`。
- `DownstreamStatusRef`（2 键）：`{ticket: integer, state: "OPEN" | "CLOSED"}`。
- `MigrationSlot`（5 键）：`{no_lost_rights: boolean, no_duplicated_capital: boolean, no_dual_write: boolean, no_resend: boolean, non_empty_evidence_refs: ArtifactRef[]}`（ADR 0063:120）。四项布尔值记对应不变量是否已由非空运行证据证实成立。已启用部署槽位缺非空运行证据时，未证实的布尔值填 `false`，`non_empty_evidence_refs` 填 `[]`（字段名表示通过条件，不是形状约束），并在 `failed_checks[]` 写明、使 `overall_result` 为 `"FAIL"`。
- `PostGateSlot`（8 键）：`{status: "NOT_TRIGGERED" | "TRIGGERED_AWAITING_POLICY" | "TRIGGERED_VERSION_AUTHORIZED" | "TRIGGERED_AND_ENABLED", gate_reached_event: ArtifactRef | null, parameter_version: ArtifactRef | null, first_activation: ArtifactRef | null, gate_reached_known_at: UtcTimestamp | null, version_authorized_at: UtcTimestamp | null, first_activation_known_at: UtcTimestamp | null, non_activation_evidence: ArtifactRef[]}`（ADR 0036:25-33）。`status="TRIGGERED_AND_ENABLED"` 时三条记录及三个时间戳均非 `null`、`non_activation_evidence` 为 `[]`，且满足 `gate_reached_known_at < version_authorized_at < first_activation_known_at` 与同 `profile_id` 互引；`status="TRIGGERED_VERSION_AUTHORIZED"` 时 `gate_reached_event`、`parameter_version`、`gate_reached_known_at` 与 `version_authorized_at` 非 `null`，满足 `gate_reached_known_at < version_authorized_at` 与同 `profile_id` 互引，`first_activation` 与 `first_activation_known_at` 为 `null`，且 `non_activation_evidence` 非空证 `growth_enabled=false`；`status="TRIGGERED_AWAITING_POLICY"` 时仅 `gate_reached_event` 与 `gate_reached_known_at` 非 `null`，其余两记录与两时间戳为 `null`，且 `non_activation_evidence` 非空证 `AwaitingPolicy{post_gate_params}` 与 `growth_enabled=false`；`status="NOT_TRIGGERED"` 时三条记录与三个时间戳全为 `null` 且 `non_activation_evidence` 非空证受测运行未触发 `GateReachedEvent` 且 `growth_enabled=false`。上述各状态对记录、时间戳与 `non_activation_evidence` 的非 `null`、非空要求是该槽位通过的条件，不是记录形状的前提。`status` 按受测运行的实际输出取值（`growth_enabled=true` 或声明闸门后参数生效时仍取 `"TRIGGERED_AND_ENABLED"`，运行证据不足以确定状态时取 `"NOT_TRIGGERED"`），缺失的记录与时间戳填 `null`，缺失的未启用证据填 `[]`，不得以占位引用代填；任一要求不满足即在 `failed_checks[]` 写明并使 `overall_result` 为 `"FAIL"`。
- `StoryCoverageEntry`（6 键）：`{story_id: string, closure_slice_ids: string[], destination_ids: string[], evidence_refs: ArtifactRef[], deferred_gates: string[], status: "VERIFIED" | "BOUNDED_DEFERRED" | "FAIL"}`。
- `FamilyCoverageEntry`（6 键）：`{family: string, id: string, entry_mode: "REQUIRED" | "OUT_OF_SCOPE_PRESERVE", evidence_refs: ArtifactRef[], deferred_gates: string[], status: "VERIFIED" | "PRESERVED_BOUNDARY" | "BOUNDED_DEFERRED" | "FAIL"}`。
