## 一、五轮 BLOCK 的共同前提

### 1.1 三条前提

**前提一：审计者可以和被审代码共用同一棵树、同一个可写目录、同一个进程。**

- 审计程序是被审包自己的构建目标〔读 `formal_math/lakefile.toml:24-31`〕。二进制落在被审包的构建目录 `formal_math/.lake/build/bin/fm_audit`〔读，240 MB〕。R5-B1 改一行 `root` 就换掉了它〔引 r5〕。
- 构建配置取自被审树，而 Lake 读配置就是执行代码。Lake 自己的源码这样写：`evaluating the project's configuration is code execution`〔读 `Lake/CLI/Main.lean:1219,1252`〕。R5-B2、R5-B3 是同一件事的两个入口〔引 r5〕。
- 源码层在审计进程里精化被审命令〔读 `SourceGates.lean:322`〕。R4-A1 的零导入 `include_str` 就是在这个进程里写了宿主机文件〔引 r4〕。
- 派生证书写在被审构建可写的目录里〔读 `run_gates.py:206-209`〕。
- 门 6b 的输入是工作树、暂存区和提交三层拼起来的，不是提交本身〔读 `run_gates.py:559-574`〕。R5-B6 出在三层没对齐〔引 r5〕。
- 还有主控没写到的一层。`ci-ok` 由 `on: pull_request` 的工作流产生〔读 `.github/workflows/ci.yml:3-8,1459`〕，这类工作流的定义取自 PR 自己。分支保护的必需检查是 `deepagents/review`、`ci-ok`、`DevSkim`，没有规则集〔测 I〕。「从受信基线取审计程序」这一步如果写在 PR 能改的工作流里，仍然由被审方决定。

**前提二：句法名单能约束精化期会发生什么。**

精化就是执行库里的程序，这批程序里有一些是通用解释器，会把被审文件里的项编译后运行。开放名单每轮都漏（第四轮），封闭名单按语料生成后大面积误拒（R5-B4）。两头都失败，错的是前提，不是名单的生成方式。核查见 3.5。

**前提三：每道阻断门都要对「任何合法 Lean 代码」成立，并按这个标准送审。**

- 说明文档对源码层写的是语义承诺：「被审代码一行不跑」〔读 `verification/README.md:45`〕、「Lean 找不到处理器，不会调用它」〔读 `README.md:48`〕、「审计期不执行被审代码」〔读 `README.md:119`〕。第四、五轮各否证了其中一条。
- 每次否证之后的返修是加一套机制，新机制带来新的承诺。`formal_math/verification` 顶层的 `.lean`、`.py`、`.tsv` 行数，五轮依次是 1197、1523、1895、2460、3925〔测 G〕。
- 「审阅者找不出洞」对「两个提交之间改了哪些路径」这种输入有限的判定可达。对定义域是一门可扩展语言的判定不可达。把两种判定放在同一个标准下送审，后一种必然 BLOCK。

### 1.2 对照主控的两条判断

- 根因一，同意，但有三处不完整。第一，信任的起点不在审计程序，在触发它的工作流，见前提一最后一条。第二，审计程序即使来自基线，只要它精化被审代码，或者和被审构建共用可写目录，仍然可以被劫持。第三，门禁的输入应当是提交，不是工作树。
- 根因二，同意放弃。不同点在放弃之后。这一层不该再承担对抗断言，也就不必再在审计进程里精化被审代码。只解析就够它该做的事〔测 B〕。
- 「拒收名单漏一个就穿」，成立。对策是任何对抗断言都不依赖名单，名单只为走捷径的作者服务。
- 「沙箱只保护宿主机，不保护审计结论」，成立。对策不是更强的沙箱。结论不能出自跑过被审代码的进程，并且要说清蓄意对手之下到底还能承诺什么，见第二节。
- 我多出的一条是前提三。它解释了为什么范围缩到可信边界之后仍然连判两次。

## 二、威胁模型与责任划分

三类对手。

- **走捷径的作者**。被要求证一条定理的代理，为了让检查变绿，会写 `sorry`、加公理、用 `native_decide`、关告警、改陈述、改锁文件、改构建配置、改门禁脚本。它用的是明文写法，不研究 Lean 内部。这是日常对手。
- **蓄意对手**。被注入或失准的代理，能找到库里的求值入口，在精化期执行自己的程序，可以伪造构建产物、干扰同一沙箱里的其它进程。
- **能改受信文件的人**。`infra/*` 分支的作者和放行它的评审。机器门对这类对手没有独立的防线，靠制度。

## 三、设计

### 3.0 运行顺序

一次运行按固定顺序走七步，前一步不绿就停。

1. 预检。只读两个提交和分支名。
2. 取料。从 git 对象生成受信目录和被审工作区。
3. 构建审计程序。源码与配置都来自基线。
4. 头部规则。审计程序只解析文件头。
5. 源码形状。审计程序只解析命令，加载的只有钉选库的环境。
6. 沙箱构建。`lake build --wfail`。被审代码从这一步才开始执行。
7. 环境层。另起沙箱，只读构建产物。公理闭包、标记、暴露、声明锁。

`lake check` 与 `lake comparator` 接在后面，归 #2315。

### 3.1 审计程序与运行脚本从哪里来

- 先定两个词。受信文件指门禁目录 `formal_math/verification/`、三个构建配置文件、`scripts/fm_env.sh` 和 `.github/workflows/formal-math.yml`。内容文件指 `Chan/`、`ChanTest/`、`ChanChallenge/`、`ChanDyn/`、`ChanExplore/` 下的 `.lean` 与 `Chan.lean`。
- 受信基线是合入目标 `main` 的当前提交。运行脚本、审计程序的 Lean 源码、它自己的 `lakefile.toml`、名单文件，全部从这个提交的 git 对象取出，放进仓库检出目录之外的受信目录。
- 审计程序改成独立的 Lake 包，放在 `formal_math/verification/` 下，只依赖工具链自带的 `Lean` 库。现有审计代码不导入 Mathlib〔读 `Audit.lean:3-8`、`SourceGates.lean:3-4`〕，拆包不需要改逻辑。被审包的 `lakefile.toml` 里不再出现 `fm_audit` 和 `FMEnvGates`。
- 运行审计程序时直接执行受信目录里的二进制，用环境变量给搜索路径。不再对被审包调用 `lake exe`。
- CI 里，触发预检的工作流必须是主干那一版。建议用 `pull_request_target` 起一个只做预检的作业。它只取 PR 的 git 对象，不检出也不执行 PR 里的任何文件，权限只要读仓库。这项检查要进分支保护的必需检查，这属于加严。内容 PR 的工作流文件既然与主干相同，后面 `pull_request` 触发的重型作业也就间接可信。
- 本地运行只作参考。脚本在输出里写明自己的代码来自哪个提交。

`infra/*` 分支改门禁自身时，机器只做三件事，剩下的交给制度。

1. 预检仍由基线版本执行。`infra` 角色只能改受信文件，不能带任何内容文件。现在的角色表允许 `infra` 改 `ChanExplore/`〔读 `run_gates.py:515-516`〕，R5-B1 的假审计程序就放在那里。`ChanExplore/` 应归内容角色。
2. 夹具单调。基线里每个 `must_red` 夹具目录在被审提交里必须是同一棵 git 树。要删或要改的逐条写进一份退役清单，交评审者。第四、五轮的审阅者每轮都在手工做这件事〔引 r4 第二节、r5 第四节第 7 条〕。
3. 被审提交的门禁在自己的全部夹具上自测通过，并在仓库现有内容上全绿。

改了受信文件的 PR，预检默认判红，读到放行标记才绿。放行标记由主控在非作者对抗评审 PASS 之后打，是记账动作，不新增人工批准门。标记的载体〔未核实〕：若执行器的令牌能打 PR 标签，标签就不独立于写代码的代理，要换成审查入口那条宿主侧通道来发布。

`main` 上还没有 `formal_math/`，所以第一片合入时没有基线版本可用，只能靠评审。这是把第一片做到最小的另一个理由。

### 3.2 构建配置怎么管

- 按内容管，不按键名。取法是「与基线同一个 git 对象」，不另设哈希清单。内容角色的 PR 里，`lakefile.toml`、`lake-manifest.json`、`lean-toolchain` 必须与基线是同一个 blob。
- 不止检查，还要改用。被审工作区里的这三个文件直接从基线取出。预检即使有洞，Lake 读到的也是主干那一份。
- 哈希清单不加防护。能改清单的角色和能改配置的角色是同一个。`pins.json` 和现在门 1 的比对可以删，用户裁定里的「版本钉选」由「与主干同一」实现，判据更严。运行中的 Lean 版本与工具链文件不符属于环境故障，退 2。
- 谁能改：只有 `infra` 角色，并且要走 3.1 的受信文件流程。
- 依赖包目录不进 git，清单里的修订号管不到缓存下来的 `.olean`。本票不给它做内容钉选。两条要求交给 #2315：沙箱里依赖目录只读挂载，这在 SafeCode 上已经这样跑通〔读 `/home/workspace/fm/r2/audit/2315/lake-check-1.log:5-6`〕；依赖内容是否可信由 `lake check` 的全量导出与重放回答。草稿里的沙箱把整个 `.lake` 挂成可写〔读 `ci/offline.sh:38`〕，CI 上依赖就在 `.lake` 里，被审代码能改 Mathlib 的 `.olean`。
- 取依赖那一步有网络，会执行依赖包的配置代码。内容 PR 用基线的配置去取，PR 的文件不参与。改了清单的 `infra` PR 要先过放行再取。

### 3.3 调用任何 `lake` 或 `lean` 之前的静态检查

全部是 Python 标准库加 git 底层命令，输入只有基线提交、被审提交、分支名。顺序如下。

1. 基线必须是被审提交的祖先，否则退 2。合入规则本来就要求追平。
2. 分支名按固定文法解析出角色。空后缀、`..`、未知前缀都不给角色。
3. 改动集合取提交对提交的原始差异，带文件模式，关掉重命名检测。不看暂存区和工作树。
4. 路径权限。每条改动（含删除）必须落在角色的路径表里。碰了 `formal_math/` 或受信文件却没有角色的分支判红。
5. 受信文件与内容文件互斥。`infra` 角色改了受信文件而没有放行标记，判红。
6. 整树形状，查被审提交的整棵 `formal_math/`，不只查改动。只许普通文件，符号链接和子模块一律红。顶层只许固定的名字。内容根下只许模块名合法的 `.lean` 文件，`lakefile.lean`、隐藏目录、`.gitattributes` 因此都进不来。
7. 内容角色下，受信文件逐个与基线比对 blob，门禁目录比对整棵树。这一步和第 4 步互为冗余，不依赖角色表写对。
8. 取料。受信目录取自基线。被审工作区的内容文件按 blob 逐个写出，配置取自基线。

三条实现约束。第一，取料不能用 `git archive` 或检出，它们会听被审树里的 `.gitattributes`。一行 `export-ignore` 就能让文件留在仓库里却不进被审工作区〔测 D〕。第二，门禁永远审一个提交，本地有未提交改动时先提交再跑。门 6b 现在的三层比对、未跟踪文件扫描、`ACCEPTED_LAYOUT` 都可以删。第三，门禁目录里不放别的角色的数据。`verification/garbage-signoffs.yaml` 归 `decl` 角色，现有代码为它写了一段专门的放行逻辑〔读 `run_gates.py:527-541,575-578`〕，挪出门禁目录之后这段可以删。

原型约 110 行，16 个用例的结果与预期一致。R5-B1、B2、B3、B6 的四种形状都在这一步判红〔测 E〕。

### 3.5 源码层

**保留。** 命令、声明、修饰符、属性、派生目标类、导入六张小白名单，都是有限集合。第五轮没有在这几张白名单上找到新洞，第四轮指出的 `#guard_msgs` 内嵌命令一项已经闭合〔引 r5 复验表 R4-A4〕。本地元编程的禁令由它们实现：没有 `macro`、`syntax`、`elab`、`notation`、`initialize` 这些命令，没有注册类属性，没有 `meta`。

**放弃。** 项与战术层的封闭名单，精化中的封表，精化后的信息树复核。

**求值入口。** 留一张点名的禁用清单，按表层语法种类和记号查：`include_str`、`eval%`、`by_elab`、`run_tac`、`run_meta`、`native_decide` 与配置项 `native`、`sudo set_option`、项级 `unsafe`、旧式 `(config := …)`、`trace`、`success_if_fail_with_msg`、占位证明。说明文档写明它是给走捷径的作者看的提示，不是防线。漏掉一个的后果由沙箱和 #2315 承担，不由它承担。

**为什么只解析就够。** 原型只加载钉选库的环境，不加载任何被审模块的产物。它逐条解析命令，只把 `namespace`、`section`、`end`、`open` 四种作用域命令交给 Lean 处理以维持解析状态，声明、项、战术都不精化〔测 B，`expB/Shape.lean`〕。

- 必绿夹具 51 个（门 2、3、6a、6b、15）零命中，零解析失败。
- R5-B4 的三份误拒汇总文件共 41 条命令，零命中。
- 门 3 的 103 个必红夹具判红 98 个。没判红的 5 个：1 个是只测环境层的夹具；1 个是 `#exit`，原型漏了一条规则；1 个是导入 `ChanExplore`，归头部方向表；2 个是库宏 `rfl'` 展开出 `smartUnfolding`，这是只解析确实看不见的，它不影响健全性。
- 门 2 的 22 个必红夹具里，10 个是源码选项写法，全部判红，含 `grind =>` 里的两个。10 个是 `lakefile` 配置写法，新设计里由预检处理。2 个靠构建告警。
- 审阅报告的 130 个夹具命中 1 个，源码里确有 `sorry`，同名夹具本来就在 `must_red/g3`。
- 代价：加载一组库导入 0.5 到 2.6 秒，常驻内存约 3.1 GiB，每个文件解析加检查 5 到 11 毫秒。全语料 522 个文件、1699 条命令、23 组导入，共 208 秒，时间主要花在 23 次进程启动上。

实现约束有三条。一个进程只加载一组库导入，文件按导入集合分组。加载库环境会运行钉选库的初始化器，它们是受信代码；被审构建的产物目录不放进搜索路径，文件头里导入的被审模块一律不加载。解析结果与真实构建不一致的风险在作用域跟踪上，自测里要有一组对照，拿必绿夹具比较只解析得到的命令数与真实精化的命令数。

**对主控那条论断的核查。** 论断是「禁止本地元编程加导入钉选之后，被审文件能触达的精化器集合就是钉选库里的那一批」。

它要拆成两句看。第一句说登记在案的精化器函数都来自钉选库，在三个条件下成立：本文件和它上游的被审模块都过了命令、属性、修饰符白名单；没有 `meta` 导入；精化期没有执行被审方提供的程序。第二句是从它推出「精化期只会发生库作者预期的事」，这一步不成立，因为那一批库函数里有通用解释器，第三个条件正是被它们打破的。

- 精化器表只有三种改法：属性登记〔读 `Lean/KeyedDeclsAttribute.lean:97-102,112-115`〕、`open` 与 `namespace` 激活带作用域的条目〔读 `Lean/ScopedEnvExtension.lean:287,329`〕、任意元程序直接改环境。前两种被白名单管住，第三种取决于有没有求值入口。
- 导入白名单不限制「那一批」的范围。只写两行 `import Mathlib.Tactic.Common` 与 `import Mathlib.Tactic.Linarith`，实际加载 2508 个模块，其中 `Lean` 769 个、Aesop 132 个、Qq 14 个、Plausible 13 个、ProofWidgets 13 个、Lake 5 个〔测 C〕。「不许导入 `Lean`、`Aesop`、`Qq`」挡的是文件头的写法，不是可达的精化器。
- 通用解释器不止说明文档点名的那几个。Aesop 的规则战术按名字对声明求值〔读 `aesop/Aesop/RuleTac/Tactic.lean:20,31,41,77`〕。`plausible` 对目标生成的检验程序求值〔读 `plausible/Plausible/Tactic.lean:204`〕，这两处能否做到任意宿主机 IO〔未核实〕。`decide +native` 与 `native_decide` 编译并运行被审的项〔读 `Lean/Meta/Native.lean:44-67`〕。钉选库源码里求值类调用点的文本检索计数约 208 处，Lean 核心 148、Mathlib 43、Aesop 7〔测 H，文本检索，偏粗〕。
- 模块制的相位检查不是屏障。`evalConst` 默认检查被求值的常量是否为 `meta`〔读 `Lean/Environment.lean:2887-2894`〕，但库里的求值入口会自己放宽它〔读 `Lean/Meta/Native.lean:60`〕，第四轮也用 `sudo set_option compiler.checkMeta false` 绕过了〔引 r4 的 R4-A1 路径四〕。
- 结论：第三个条件没法靠一张名单证明，这条论断只能支撑诚实作者断言。

4.36.0 有两个对设计有利的事实。内核里已经没有原生求值钩子，自己声明一个 `Lean.reduceBool` 不会让内核去运行编译产物〔测 A3〕。`native_decide` 不再经由 `Lean.ofReduceBool`，它在本模块里落一条形如 `t._native.native_decide.ax_1_1` 的公理〔测 A3〕。票面与现有代码里写的 `Lean.ofReduceBool`、`Lean.trustCompiler` 在这个版本里已不存在，环境层按「标准三条之外的公理一律红」判就够。

### 3.6 环境层够不够兜底

对走捷径的作者，够。`sorry`、公理、`native_decide` 都落在公理闭包里。`unsafe`、`partial`、`implemented_by`、`extern` 落在标记里。走捷径的作者不伪造产物，`lake build` 自己的内核检查对它是真的。

对蓄意对手，不够。环境层事后看不见五类东西。

1. 没经内核检查的常量。实验里用一段元程序在关掉内核检查的情况下塞进 `Toy.forged : False`，再用它证出 `1 = 2`。这段元程序模拟的是求值入口到手之后能做的事。`lake build` 通过，两条定理的公理闭包都是空的，内核重放报类型不符〔测 A2〕。
2. 不进环境的东西。`example`、`#check`、被吞掉的告警、项内改了又恢复的选项。
3. 精化期的副作用。宿主机读写、改写别的模块的产物、干扰同一沙箱里的进程。
4. 产物与源码不对应。被审代码改写另一个模块的 `.olean` 之后，产物里是一批内核认可、但和源码文字不同的声明。重放也看不出来。
5. 审计程序读 `.olean` 这件事本身。`.olean` 是直接映射进内存的对象图，畸形文件可能破坏读取它的进程〔未核实，推断〕。Lake 上游的做法是裁决进程不映射任何被审 `.olean`，只读文本导出〔读 `Lake/CLI/Check.lean:30-32`〕。

审计程序读环境的方式本身不执行被审代码。`importModules` 默认不加载扩展，此时模块里的 `initialize` 不运行；实验里带初始化器的模块，这样读不落哨兵文件，打开扩展加载才落〔测 A1〕〔读 `Lean/Environment.lean:2797-2810`、`Lean/Compiler/InitAttr.lean:199-201`〕。库定理证明体里的公理依赖要按私有层级加载才看得见，现有实现是这样做的〔读 `Audit.lean:183-184`〕。

所以蓄意对手之下的承诺要这样写。任何一条定理，只有当它的陈述写在锁定目录里、由 `lake comparator` 在一个被审代码没有写过的构建目录里先构建挑战模块、再比对并交给内核重放，才算端到端成立。其余定理的承诺是「构建诚实时成立」。这和项目把最终陈述放在 `ChanChallenge/`、证明放在别处的结构是一致的。

对 #2315 的三条硬要求。

1. 必需检查由主干版本的工作流产生，并且对每个 PR 都给出结果，不碰 `formal_math/` 的 PR 直接绿。草稿用了 `paths:` 过滤〔读 `formal-math.yml:19-23`〕，按 GitHub 文档，被过滤掉的必需检查会一直停在等待状态，本次没有实测。重型作业的检查也要设为必需，定义放在受信的工作流文件里，不并入 `ci-ok`，因为 `ci.yml` 不是受信文件。
2. 沙箱里依赖目录只读。审计程序与被审构建不共用可写目录。
3. `lake comparator` 的 `definition_names` 留空，它的配置文件归 `decl` 角色或受信文件。挑战模块在被审代码从未写过的构建目录里先构建。现在草稿把它排在阻断门和 `lake check` 之后、共用同一个 `.lake`〔读 `formal-math.yml:183,186`〕，而它在挑战和解答之间不清构建目录〔读 `Lake/CLI/Check.lean:529-538,356-375`〕。

另有三件事 #2315 要知道。`lake check` 只查默认目标〔读 `Lake/CLI/Main.lean:1233-1241`〕，预检的形状规则要保证每个内容文件都落在默认目标里。它的公理核对只报被别的常量引用的公理〔读 `Lake/Check/Axioms.lean:60-71`〕，没被引用的公理声明要靠环境层。它的构建和导出在同一个沙箱进程树里〔读 `Lake/CLI/Check.lean:338-354`〕，蓄意对手可以伪造导出流，所以单独的 `lake check` 也只在构建诚实时成立，绑定陈述的是 comparator。

关于 PR 上的内核重放。工具链自带的 `leanchecker` 给前缀目标时稳定段错误：`leanchecker Chan` 和 `leanchecker Chan ChanTest` 三次都退 139，单模块和两个互不导入的模块正常〔测 F〕。前缀匹配又使父模块无法单独选中〔读 `LeanChecker.lean:92-130`〕。建议本票不自带重放，`lake check` 放在 PR 上跑，约 10 分钟、1.9 GiB〔引 #2315〕。草稿只在推到 `main` 之后跑它〔读 `formal-math.yml:183`〕，那是事后告警，不是合入门。给不起这 10 分钟时，可以在审计程序里顺序调用 `Lean.Kernel.Environment.replay`，实验 A2 用的就是它，约二三十行；因为内核没有原生求值钩子，进程内重放不会执行被审代码。

### 3.7 退出码契约

- 0：七步都跑完且全绿。1：某一步有判红。2：无法判定，包括工具缺失、崩溃、超时、输出无法解读、前置条件不满足。CI 把非零一律当失败，1 和 2 的区别只给人看。
- 快速失败。第一个不绿的步骤结束整次运行，后面的步骤不跑也不报。一步的红因此不会让另一步报「无法判定」，R5-B5 第一项不再可能出现。
- 不再有「只跑某一道门」。只有「跑到第几步为止」，因为后一步的含义依赖前一步为绿。
- 运行脚本不凭审计程序的退出码下结论。审计程序每个子命令必须在标准输出给出一份结构化结果，写明判定、发现列表、审过的模块数。运行脚本拿模块数和自己从 git 树里数出来的比对，对不上或解读不了就退 2。
- 红行格式固定，一行一条，带步骤名、路径、位置、红码。诊断写标准错误。
- 自测断言的是整次运行的退出码和红码集合。第五轮的教训是自测只测单门，默认全跑从来没被测过〔引 r5 的 R5-B5 第 1 项〕。

## 五、实现与送审的切法

前几张受审实物的共同问题是返修只增不减，而且一张实物里混着两种断言。建议切成五片，每片只带一种断言，先定夹具再派实现，返修只许删代码或改本片文件，要新机制就另开一片。

1. **预检。** 纯 Python 加 git，目标两百行以内。夹具是自测现场造的小 git 仓库，现成的有 R5-B1、B2、B3、B6 和附录 A 的 16 例。对抗断言。送审问题只有一个：能否构造基线、被审提交、分支名三元组，使预检退 0，而某个受信文件与基线不同、或有角色之外的路径被改、或 `formal_math/` 下出现形状规则之外的文件。先做这一片。它独立于 Lean，它一合入就开始审后面四片，它也是 `main` 上第一份受信文件。
2. **运行骨架。** 取料、七步顺序、退出码契约、审计程序拆成独立包。Lean 逻辑不动。送审问题：被审树能否影响哪个审计二进制被执行，或者经声明之外的通道影响它的输入。
3. **环境层搬家。** 现有 `Audit.lean` 的门 3、声明锁、暴露检查原样搬进独立包，派生证书改用声明范围。差异应当很小，第五轮核实过的逻辑不重写。
4. **源码形状门。** 用只解析替换现有的精化式检查，同一个 PR 里删掉 3.4 列出的那些文件。诚实作者断言。夹具是现有必红必绿语料，加上 R5-B4 的 41 条。两个 `rfl'` 夹具转成「已知不防」夹具，期望为绿并写明谁接。
5. **说明文档与交接。** 每道门一行，四列：断言、对手、不防什么、谁接。给 #2315 的三条要求写进它的验收。

送审说明要随断言类别改写。对抗断言的门，找到任何绕过都是 BLOCK。诚实作者断言的门，BLOCK 的条件只有三种：点名的写法以明文形式出现却没判红；必绿语料被误拒；「不防什么」写得不如实，或者写了由谁接而接的那一层实际接不住。用库里冷僻的精化器绕过源码形状门，不构成 BLOCK，除非能说明后果没有人接。

## 六、最可能被第六轮击穿的三处

**第一处：信任的起点没有落到主干上。** 预检如果仍由 PR 自己的工作流触发，审阅者只要让 PR 改掉工作流就全绿，和 R5-B1 同形。提前处理：把「必需检查由主干版本的工作流产生」列为 #2315 的验收条件，配一个必红用例，`proof/*` 分支改 `formal-math.yml`，结果必须是必需检查失败。`pull_request_target` 的检查能否设为必需、检查挂在哪个提交上〔未核实〕，要在 GitHub 上实跑一次。跑不通的退路是仿照 `deepagents/review`，由宿主侧进程发布这项状态。

**第二处：诚实作者断言被当成对抗断言来审。** 审阅者拿一个清单外的求值入口伪造了某个非锁定定理的产物，全部门禁通过，然后指出这违背票面「进入主干的定理确实被内核接受」。这在我的设计里是写明的「不防」，但如果送审说明和说明文档没有事先写明，结果仍是 BLOCK。提前处理三件事。把票面目标改写成两句，「构建诚实时全部定理成立」与「蓄意对手之下 comparator 绑定的陈述成立」，并请用户或主控确认这个改写。把已知的绕过做成「已知不防」夹具，每个配一条测试，证明接手的那一层确实接住了，例如沙箱外哨兵文件不存在、重放判红。送审说明按第五节的三个条件写。

**第三处：只解析与真实精化之间的解析差异，以及预检的路径文法。** 两处都是「自写的判定和真实工具对同一输入理解不同」。只解析这边，作用域跟踪如果和 Lean 不一致，轻则误拒，重则让一段文本在审计程序眼里是一种语法、在编译器眼里是另一种。提前处理：解析失败一律红；自测里对全部必绿语料比对命令数；一个进程只加载一组与该文件完全相同的库导入，不用并集环境。预检这边，风险在路径大小写、Unicode 规范化、分支名边角、角色表前缀写得过宽，现表里 `.github/workflows/` 整个目录归 `infra`，连 `ci.yml` 也在内〔读 `run_gates.py:515`〕。提前处理：路径与分支名用白名单文法，受信文件逐个列全名，顶层名字用固定集合，3.3 的第 4 步与第 7 步互为冗余。
